# 「【29-4Q】ロンザンPDCA管理」スプレッドシートの構造

対象: スプレッドシート「【29-4Q】ロンザンPDCA管理」(`1lA8VibWomv9igeYYAACvumFx-Jv1WbSLmbiRJdKWJl8`)。2026-08-18に「個人別タブの特定セルの数値が反映されない」という問い合わせを調査した際に判明した構造をまとめる。[docs/business-structure.md](business-structure.md)の営業ファネル(初期交渉→マッチング→設定→本交渉→成約)のうち、**「マッチング(実提案)→設定(本交渉設定)」に至る前段階の指標**を、企業担当の承認プロセスまで含めて詳細に管理しているシート。[spreadsheet-shoki-seisansei-structure.md](spreadsheet-shoki-seisansei-structure.md)(初期交渉生産性シート、本交渉発生日ベースの実績集計)とは別のスプレッドシートで、バックエンドのシート名(shoki/matching/hon/masta等)が同じでも中身・列構成は共有されていない点に注意。

## 1. このシートが管理している指標の位置づけ

企業への「実提案」に至るまでの候補者集客・マッチングルートは3系統あり、このシートはそれぞれを並行してPDCA管理している。

```
[初期交渉ルート]     初期交渉実施 → 初期交渉からの提案数 → 候補者企業担当◯ → 実提案数 → 提案からの設定数
[反響ルート]         展開件数 → 反響件数 → 反響からの実提案数 → 反響からの設定件数
[他人マッチングルート] 他人候補者マッチングからの提案数 → 他人マ候補者企業担当◯ → 他人マ候補者実提案数 → 他人マ候補者提案からの設定数
```

- **初期交渉ルート**: 自分が候補者担当として初期交渉を行った候補者を、自分自身でマッチング(提案)させる流れ(matchingシートの`自/他`列が「自」)。
- **他人マッチングルート**: 自分は企業担当として、別の候補者担当が抱える候補者のマッチングを受け入れる流れ(`自/他`列が「他」)。同じ4ステップ構造だが主体が逆(候補者担当→企業担当)。
- **反響ルート**: 候補者への求人紹介の「展開」に対して候補者側から反応(反響)があった案件を起点とする、初期交渉を介さない別チャネル(tenkaiシートが起点データ)。

いずれも最終ステップの「設定」は[business-structure.md](business-structure.md)でいう「本交渉設定」に相当する。「企業担当◯」は、企業担当者が候補者の提案を承認(◯判定)したことを指すマイルストーンで、初期交渉ルート・他人マッチングルートにのみ存在し(反響ルートには対応する行がない)、マッチング→実提案の間に企業側の意思決定ステップが挟まることを表している。

各集計粒度タブとも、G列以降は**KPI1種類につき2列(実績・予定)のペア**になっている(1行目がKPI名のマージセル、2行目が「実」/「予」)。

## 4. 【個人別】タブの行構造(人ブロック)

2326行は、**1人あたり約26行のブロックが人数分繰り返す**構造になっている。

```
row N    : ヘッダー行  A列=人物インデックス(前ブロックの続き番号) B列=xlookup(A列, masta!Z:Z, masta!AA:AA)で人名を取得
row N+1  : (空白)
row N+2  : 7月1W  ← A/B列に開始日/終了日、C列に「7月1W」等のラベル、G〜AN列の代表セルにMAP+LAMBDA数式
row N+3  : 7月2W
row N+4  : 7月3W
row N+5  : 7月4W
row N+6  : 7月5W
row N+7  : (7月の週次合計行。ラベルなし、=sum(週次行)の隠し行)
row N+8  : (空白)
row N+9〜N+14 : 8月1W〜5W + 週次合計
row N+15 : (空白)
row N+16〜N+21: 9月1W〜5W + 週次合計
row N+22 : (空白×2)
row N+24 : 7月(月次平均行。 =iferror(週次合計/countifs(週次行,">0"),"-") で「稼働した週の平均」を出す)
row N+25 : 8月
row N+26 : 9月
```

(行オフセットは実データで確認した1ブロック分の実例。ブロック間の空白行数がわずかに異なる可能性があるため、新しい月・新しい人のブロックを扱う際は必ずC列のラベルで位置を確認すること。)

**代表セル+MAP/LAMBDA方式**: G〜AN列の「実」列は、各月の最初の週(1W)の行(上記でいうrow N+2, N+9, N+16)にのみ実際の数式が入っており、`map($A(1W行):$A(5W行),$B(1W行):$B(5W行),lambda(start,end,...))`で1W〜5W行にスピル展開される(残りの行のセルは値のみでFORMULA取得すると空になる)。[CLAUDE.md](../CLAUDE.md)の「KPI分析時の注意点」で説明している「代表セルのコピペミス」の落とし穴がここでも当てはまる。

## 6. 既知の不具合と修正(2026-08-18)

**不具合の内容**: G/I/K/M/O/Y/AA/AC/AE/AG/AI/AK/AM の13列すべての代表セル数式が、週の終了日を`countifs(...,"<="&end,...)`という条件で絞り込んでいた。`end`は時刻成分のない日付整数だが、参照先(matching!B/jitsuteian!L,M/hon!E/tenkai!C等)の日付列には時刻成分(例: `2026/07/31 11:07`)が入っているケースがあり、**「週の最終日ちょうどに、かつ00:00ちょうどでない時刻に発生したイベント」が`<=end`を満たさず、集計から漏れる**という潜在バグがあった。最終日が休業日(日曜日等)に当たることが多く、めったに発生しないため長期間気づかれていなかった。

**発覚の経緯**: 2026年7月度の「7月5W」(7/27〜7/31)で、7/31に発生した2件のマッチング(matching_id: 127609, 127610)が個人別タブI732に反映されない、という問い合わせから発覚。

**修正内容**: 全条件を`"<="&end` → `"<"&(end+1)`に統一(翌日0時未満、という条件にすることで時刻成分の有無に関わらず正しく期間内と判定されるようにした)。93人×3ヶ月(7月/8月/9月)×13列 = 3,627セット中、3,626セットを一括置換(1セットは発覚時に個別修正済み)。修正漏れ・数式エラーとも0件を確認。

**注意点**: 同じ「代表セル+MAP/LAMBDA、日付範囲countifs」のパターンは、Q/S/U/W(転換率列)や、他の集計粒度タブ(【課別】【T別】【全体/職種別×週次/日次】)、さらには本シート以外の管理シート(例: [spreadsheet-shoki-seisansei-structure.md](spreadsheet-shoki-seisansei-structure.md)で扱う初期交渉生産性シート)にも存在しうる。「期間の合計値が想定より少ない」「特定の週だけ計上漏れがある」といった相談が来た場合、[CLAUDE.md](../CLAUDE.md)の「代表セルのコピペミス」チェックに加えて、**この「期間最終日+時刻成分」パターンも疑うこと**。判定方法: 疑わしい代表セルの数式を`FORMULA`レンダリングで取得し、`"<="&`(または`"<="&変数名`)の形の日付上限条件がないか確認する。あれば、参照先の日付列の実データ(`UNFORMATTED_VALUE`)に小数(時刻)成分が含まれていないか確認し、含まれていれば同様の修正が必要。

なお、【課別】【T別】【全体/職種別×週次/日次】タブの実績列(G列相当)は本シート内で独自に日付範囲countifsを行っているのではなく、【個人別】タブの値を課/T/職種で集約する形と見られ(未確認)、「予」列はplan_export/plan_MiddleKigyoシートを週ラベルで参照する別方式(日付範囲ではなく完全一致)のため、このバグの対象外である可能性が高い。
